========== LENS: structured-output ==========
AREA: Structured output &amp; result validation (structured-output)

CURRENT BEHAVIOR (source-grounded):
A worker/reviewer/overseer result reaches validated harness state via PARSE-THEN-VALIDATE of a driver-written artifact, NOT a forced structured-output tool call enforced at the tool layer. The contract differs per driver, and there is NO harness-level self-retry on malformed output.

Two distinct extraction paths exist:

(1) codex driver (src/worker-driver.ts:60-112): the harness passes `--output-schema <schemaPath> --output-last-message <resultPath>` (lines 79, 97) and lets the codex CLI write the final message to a file. `finalize()` (101-111) then calls `validateResultArtifact()` (116-139): it `fs.existsSync` the file, `JSON.parse`es it (122), and `schema.safeParse`es it (133) against `spec.resultSchema ?? workerResultSchema`. So validation is purely on a file the child process produced; the schema is advisory to codex, enforced only post-hoc by the harness.

(2) claude driver (src/worker-driver.ts:169-252): the harness passes `--json-schema <schemaJson>` and reads `--output-format stream-json`. `finalize()` (219-251) scans stdout backwards via `lastResultEvent()` (147-164) for the `type:"result"` event, reads `resultEvent.structured_output`, `safeParse`es it (225), and on success WRITES it to `spec.resultPath` itself (227). So claude's path does consult a model-emitted `structured_output` field, but the harness still validates after the fact and is responsible for persisting the artifact.

(3) fixture driver: bypasses all of this — `runFixtureWorker` returns a typed object in-process and the CLI does `fs.writeFileSync(lastMessagePath, JSON.stringify(workerResult))` then hardcodes `finalization = { ok: true, structuredResultWritten: true }` (src/cli.ts:2360-2366; review 2607-2618; overseer 2079-2086). No validation at all on the fixture path.

The artifact is then validated a SECOND time when consumed: `readReviewResultFile` (cli.ts:3846-3865), `readOverseerDecisionFile` (5667-5686), and the worker-result verifier (4326-4345) each independently `JSON.parse` + `schema.safeParse` the same file. The JSON Schema handed to drivers is HAND-WRITTEN separately from the Zod schema in `writeWorkerResultSchema`/`writeReviewResultSchema`/`writeOverseerDecisionSchema` (cli.ts:6460-6611) — two parallel definitions of the same contract that can drift.

On malformed output the behavior is BLOCK, never retry: worker `finalize.ok=false` -> slice status "blocked" (cli.ts:2464); review parse failure -> slice "blocked", dependencies blocked, blocker escalation inserted (2740-2744); overseer parse failure -> `overseer.failed` event + blocked heartbeat (2183-2219). Recovery from a malformed result is operator-driven (recovery revive/restart commands), not an automatic same-call re-ask. There is one silent-success edge: codex `finalize` returns `ok` based ONLY on artifact validity and treats a non-zero exit code as a recoverable success (`resultArtifactRecoveryReason`, worker-driver.ts:141-145) — a valid file overrides a crashed process.

========== LENS: resume-idempotency ==========
AREA: Resume, recovery &amp; idempotency (resume-idempotency)

CURRENT BEHAVIOR (source-grounded):
Recovery in agent-swarm is SESSION/RUN-level and operator-driven, not step-memoized. The pipeline is: (1) `swarm recovery scan` ages every `running` agent_run against a heartbeat staleness threshold (focus.ts findStaleAgentRuns at cli.ts:3340-3361; threshold from protocol at cli.ts:3311-3314). With `--mark-stale`/`--release` it mutates the run to `stale`/`released`, sets the affected slice to `blocked`/`closed`, raises a scoped blocker escalation (deduped by checking the run id appears in an existing active escalation, cli.ts:1526-1542), and refreshes a `recovery` checkpoint. (2) `swarm recovery revive <run-id>` resumes the SAME provider session: it requires the driver to advertise `capabilities.resume` (worker-driver.ts: codex+claude both true) and a captured `sessionId` (from the run row, else re-extracted from the run's JSONL via sessionIdFromAgentRunEvents at cli.ts:1916-1919), then spawns a NEW agentRun row (a fresh RUN id, attempt = prior-runs-for-(slice,actor)+1, cli.ts:1599) passing `resumeSessionId` so codex `exec resume <id>` / claude `--resume <id>` continues the model's own context (worker-driver.ts:69-82, 198). (3) `swarm recovery restart <run-id>` discards the session and calls executeWorkerRun with reason='restart' for a brand-new run on the same slice (cli.ts:1833-1842). On a successful revive/restart, superseded recovery escalations are cleared by substring-matching the prior run id (clearSupersededRecoveryEscalations, cli.ts:1879-1914).

Durable resume context is REGENERATED from the SQLite ledger on demand, never replayed: `swarm resume-context` (cli.ts:1342-1364) calls buildResumePacket (checkpoints.ts:43-105), which derives a role-specific markdown packet (objective, FR/AC scope, evidence status, blockers, artifact paths, doNotRedo, reviveRecommendation) purely from current store rows. Checkpoints are an upserted SNAPSHOT keyed unique(role,entity_type,entity_id) (storage.ts:188-199, 639-662) — there is exactly one row per (role,entity), overwritten each refresh, not an append-only journal. focus.ts builds richer run/slice "focus packets" (buildRunFocusPacket/buildSliceFocusPacket) and classifies failures (no_event_stream, child_idle_timeout, missing_structured_result, etc., focus.ts:477-509) to recommend revive vs restart, but these are advisory diagnostics, not memoized results.

There is NO content-addressed step-level memoization. Every dispatch unconditionally spawns the provider: `swarm run <slice>` -> executeWorkerRun(reason='direct_run') (cli.ts:828-850, 2253-) has no guard for an already-implemented/accepted slice and no prompt-hash lookup; it always writes a new prompt, inserts a new agentRun, and on success ALWAYS inserts a fresh worker_result evidence row (insertEvidence is a plain INSERT with a random EVD id, storage.ts:552-559; cli.ts:2423-2433). Re-running an identical worker/reviewer/verify unit re-does the model work and appends duplicate evidence — re-running a step is NOT idempotent in storage. Worker/reviewer results are obtained by PARSE-THEN-VALIDATE, not a forced-tool self-retry loop: drivers point the provider at an output schema file and read the resulting on-disk artifact (codex `--output-schema/--output-last-message`) or the `structured_output` field of claude's result event, then run Zod safeParse (worker-driver.ts:116-139, 219-251 against workerResultSchema, schemas.ts:38-53). On safeParse failure the run is simply marked `failed` with a failureReason; the harness itself does not auto-retry — a human/overseer decides revive or restart. IDs are random UUIDs (ids.ts:19) and every write stamps `new Date().toISOString()`, so runs are inherently non-replayable and non-deterministic at the storage layer.

WORKFLOW COMPARISON:
Workflow mechanism 2 (content-addressed result journal) keys every agent() call by v2:sha256(prompt+opts), stores the VALIDATED result under that key in journal.jsonl, and on resume replays unchanged steps for free, re-running only from the first changed call onward — exact, cheap, step-level memoization. agent-swarm has essentially the inverse model on the resume/idempotency axis. On schema enforcement (mechanism 3) the comparison is partial: agent-swarm forces structured output via an output-schema file + Zod validation, but validation is post-hoc parse-then-validate that marks failure, NOT the tool-layer self-retry-until-valid loop Workflow uses, so the model does not auto-correct in-harness.

========== LENS: orchestration-controlflow ==========
AREA: Orchestration control flow (LLM vs code)

CURRENT BEHAVIOR (source-grounded):
The overseer is NOT a "LLM-proposes-nextCommand-each-turn" agent loop, and it is NOT a fully scripted control plane either — it is a deterministic JS loop with a single-shot LLM leaf per iteration whose job is largely to re-select a command the code has already computed.

The control loop lives in the demo runner scripts, not in src/. run-live-agent-demo.mjs:229 is `for (let turn=1; turn<=maxTurns; turn++)`. Each iteration runs, in order: (a) deterministic guards — source-mutation check, max-slices/max-agent-runs/max-runtime limits (run-live-agent-demo.mjs:231-258); (b) deterministic fault handlers — handleStaleRunFault, handleSupervisedRecovery, handleContextHandoffFault, handleLowSignalFault (260-282), each of which dispatches harness commands (e.g. `recovery scan --mark-stale`) with NO LLM involved; (c) deterministic verification when a slice isReadyForDeterministicVerify (332-411), calling `swarm verify` directly and computing accept/block from gates; and only then (d) ONE call to `swarm orchestrate ... --execute` (413-424), the single LLM overseer turn. The loop, not the LLM, decides termination, verification, recovery, and limits.

Inside the harness, executeOverseerRun (cli.ts:1979-2251) is single-shot: build prompt -> run exactly one driver turn (or fixture) -> parse one OverseerDecision -> applyOverseerDecision -> optionally execute up to executeLimit bounded commands -> return. There is no inner LLM loop and no per-turn re-planning by the model.

Crucially, the deterministic code already computes the very decision the LLM is asked to make. buildOverseerStatePacket (cli.ts:4882-5080) precomputes, for each active slice, an exact `nextCommand` + `nextCommandPurpose` (cli.ts:4911-4921: ready/blocked/repairing -> `run <slice> --actor ... --driver codex`; implemented/ready_for_review -> `review <slice> ...`), plus a `nextSourcePullQueue` whose items each carry a ready-to-run `slices pull` nextCommand (cli.ts:5252), a blockedSourceQueue with prerequisiteCommands, and a focusQueue. The prompt's "Decision discipline" (cli.ts:5440-5450) then instructs the model to "recommend that exact command first" from activeSliceQueue/nextSourcePullQueue. After the model answers, validateOverseerCommand (cli.ts:6038-6109) deterministically re-derives the same legality the packet encoded — allowlisted subcommand, slice status gating (validateOverseerChildDispatch cli.ts:6174-6232: run requires ready/blocked/repairing, review requires implemented/ready_for_review + existing worker_result evidence + no running child), pull dependency satisfaction (validateSlicesPullDependencies cli.ts:6135-6150), no shell operators — and blocks anything off-script. So the LLM operates strictly inside a deterministically-precomputed, deterministically-revalidated envelope; its degrees of freedom are mostly ordering/blocking judgement and escalation prose.

That the LLM is structurally optional for the happy path is proven by run-live-agent-scripted-demo.mjs, which drives the full pull -> run -> review -> verify lifecycle with zero overseer LLM (scripted-demo lines 41-60), and by the fixture overseer runFixtureOverseerDecision (cli.ts:5559-5665), a pure-code stand-in that picks the same commands.

Output handling matches Workflow mechanism 3 (schema-enforced): codex is forced via `--output-schema`+`--output-last-message` and validated by zod (worker-driver.ts:101-138); claude is forced via `--json-schema` producing StructuredOutput, validated and written (worker-driver.ts:219-251); the harness then re-validates with overseerDecisionSchema in readOverseerDecisionFile (cli.ts:5667-5686). There is no content-addressed result journal / step memoization (no journal.jsonl, no v2:sha256(prompt) keying anywhere in src — Workflow mechanism 2 is absent); resume is instead handled by checkpoints/resume-packets. The loop also uses Date.now()/new Date() freely (18 occurrences in run-live-agent-demo.mjs), the opposite of Workflow mechanism 1's determinism ban.

WORKFLOW COMPARISON:
Workflow mechanism 1 says the control plane is deterministic JS (loops/parallel/pipeline) and the LLM only fills leaves; agent-swarm already realizes the SPIRIT of this: the turn loop, fault recovery, verification, and limits are deterministic JS, and the overseer is a single-shot leaf. But there are three divergences. (1) The "leaf" is over-scoped: the code precomputes the exact nextCommand and then asks an LLM to pick it from a queue, then re-validates it — so an LLM round-trip is spent re-deriving a deterministic answer. 4) Repair dispatch: a `repairing` slice is fed back through `buildSliceRepairContext` (cli.ts:4166-4202), whose `latestRepairReviewContext` lifts the reviewer's `requiredFixes`/`recommendation`/nonPassingRefs straight into the next worker prompt (cli.ts:6408-6414, 5443). 5) Human path (the observed `human_verification_rework` loop): when an obligation has mode human_verification_required, `buildFrAcResults` marks the ref `awaiting_human_verification` (cli.ts:4450-4458). A human records human_verified|failed|needs_rework via `recordHumanVerification` (human-actions.ts:176-334). A `failed`/`needs_rework` decision sets the slice to `repairing`/`blocked` (human-actions.ts:231) and the queue then renders a `human_verification_rework` action whose summary literally says "Continue the run so agents can repair the slice" (human-actions.ts:388-419) and feeds `latestHumanRepairFeedback` into the repair worker (cli.ts:4204-4222). A false or out-of-scope human "failed" thus drives a fresh worker repair with zero challenge; on the next cycle the ref is re-packetized to `awaiting_human_verification` again -> the repeated rework loop.

The only thing resembling adversarial filtering is the overseer's `getOverseerEscalationSuppressionReason` (cli.ts:5751-5774) which de-dupes overseer-raised blockers; it does not judge reviewer/human finding actionability and runs only on the overseer's own blocker list.

WORKFLOW COMPARISON:
Workflow mechanism 7 (adversarial verify on actionability) runs a per-finding skeptic that DEFAULTS TO REJECT and must be convinced a finding is genuine AND worth acting on now; in the forensic run it killed a finding that was factually correct but pre-existing/out-of-scope, filtering true-but-not-worth-acting-on noise BEFORE it reached any work queue.

agent-swarm has the inverse posture: findings default to ACCEPT. The Sleuth Review Gate is a strong single judge, but it is the SAME agent that produces both the finding and the verdict — there is no independent challenger between "reviewer/human emitted finding" and "finding drives `repairing` + escalation + human queue." There are zero concurrency primitives in src/ (no Promise.all/race/allSettled, no worker pool, no in-flight counter; grep over src returns nothing). Three nested serialization points:

(1) TOP-LEVEL RUN LOOP (scripts/run-live-agent-demo.mjs:229 `for (let turn = 1; turn <= maxTurns; turn += 1)`): a single sequential turn counter. Each turn does at most ONE action and almost always `continue`s to the next turn: it observes state, then either handles one fault, or verifies the ONE slice returned by `before.slices.find(isReadyForDeterministicVerify)` (line 332 — find, not filter, so one slice per turn), or runs ONE overseer turn (line 413). Slices are advanced strictly one-at-a-time, one stage per turn; there is no pipelining of distinct slices through distinct stages simultaneously.

(2) OVERSEER COMMAND LOOP (src/cli.ts:5877 `for (let index = 0; index < commands.length; index += 1)`): the bounded commands an overseer recommends (capped by executeLimit, default 3) run in a sequential for-loop, each via a BLOCKING `spawnSync(process.execPath, [process.argv[1], ...cliArgs])` (line 5941). A child-agent dispatch (a nested `swarm run`/`swarm review`) therefore blocks the parent overseer process until that worker/reviewer fully completes before the next command is even started.

(3) PER-SLICE CHILD AGENT (src/cli.ts:2828 spawnWorkerStreaming returns a single awaited Promise resolved on child `close`): exactly one child process is in flight per executeWorkerRun/executeReviewRun call, and the caller awaits it. There is also an EXPLICIT guard (src/cli.ts:6204-6218) that REFUSES to dispatch a child agent if any worker/reviewer run for that slice is already `running` — so worker→review→verify for a single slice is contractually sequential (this is a correct evidence-ordering invariant, not a perf bug).

The planner (src/planner.ts:45 pullNextSlice) is invoked one slice at a time via the `swarm slices pull` CLI command (cli.ts:743) or by the overseer recommending it; it does not batch-create or schedule multiple slices for parallel work. `firstActiveLaneForTarget` (planner.ts:133, storage.ts:328 `... limit 1`) reuses a single active lane by default, so the default planning path funnels everything through one lane. The protocol declares `lanes.maxActiveLanes: 3` (protocol.ts:53, protocol.yaml:12) but this value is NEVER read or enforced anywhere in src (grep for `maxActiveLanes` hits only protocol.ts default, docs, never planner/storage/cli) — there is no lane-level WIP/concurrency control in code at all; it is dead config.

WORKFLOW COMPARISON:
Workflow mechanism 4 (pipeline-no-barrier) says each item flows through ALL stages independently, so wall-clock equals the slowest single chain, not the sum of stage maxes; verifiers can run while a slow reviewer is still working on a different item. agent-swarm is the opposite extreme of even a barrier model: it has neither pipelining NOR fan-out batching. It does not "wait for all workers then review" (barrier) — it never has more than one worker at a time to wait for. Wall-clock = SUM over every slice of (worker + review + verify), fully serialized, plus an extra overseer LLM turn between most stages (the loop almost always does one action then `continue`s, re-invoking the overseer to decide the next single action). Compared to Workflow's content-addressed journal + pipeline that lets N items progress through M stages concurrently with wall-clock ≈ slowest chain, agent-swarm's wall-clock for K slices is roughly K × (overseer-turn + stage latencies) summed. The mission's parallel ambition ("coordinate autonomous implementation agents AT SCALE", lanes as parallel work streams) is structurally unrealized: lanes exist as a data/ownership concept but carry no execution concurrency. The one place agent-swarm is correctly stricter than a naive pipeline is the per-slice worker→review→verify ordering and the "no dispatch while running" guard (cli.ts:6204) — those preserve the evidence-ordering and "workers may not approve their own verification" invariants and must be retained under any parallelization.

========== LENS: context-packets ==========
AREA: Context packets (shared facts and no-redo guard)

CURRENT BEHAVIOR (source-grounded):
Agent-swarm builds four packet types, but they are NOT a unified shared-CONTEXT-with-already-verified-guard the way Workflow mechanism 5 implies. (1) WORKER PROMPTS: buildWorkerPrompt (cli.ts:6320-6388) hand-assembles markdown from the SliceRecord: target, lane, skill packet text, slice id/title, deliveryQuestion, work package, immutable sourceRefs, frAcRefs, read-only verification obligations (formatVerificationObligations cli.ts:4710), scope/outOfScope/expectedEvidence/verificationRequirements, then formatRepairContextForPrompt, then static instructions.
